## ⚠ 零之零、推送前必须处理：历史里有局域网令牌

本仓库是 **public**。当前工作区已经清干净（`git grep` 查不到），但**本地历史里
仍有真实令牌**：

```
含本机网关令牌的提交: 9 个
含对端网关令牌的提交: 5 个
```

直接 `git merge --no-ff` + `push` 会把这些提交推上公开仓库，令牌就陆续进了
GitHub 的历史（即使后来改了文件，历史里依然可查）。

**已定：方案 A（squash 合并）。** 下面是为什么，以及 B 是什么（留档，不采用）。

### 方案 A（推荐，最简单）：squash 合并

```powershell
git checkout main
git merge --squash feat/model-gateway-phone-polish
git commit -m "feat: v2.6.6 局域网模型共享加固"
```

- 公开仓库只看到**一个**提交，内容是最终代码树（已无令牌）；
- 93 个细分提交只留在本地分支，不推送；
- 代价：GitHub 上没有逐条历史。

**方案 A 已预演验证通过**（2026-11-26 03:3x，在临时分支上做的，已清理）：

```
git merge --squash feat/model-gateway-phone-polish  -> 无冲突
git commit -m "..."                                 -> 相对 main 只有 1 个提交
git grep <令牌>                                     -> 树里无令牌
git log main..HEAD -S <令牌>                         -> 0 个提交含令牌（本机与对端都是 0）
git diff <squash> feat/... --stat                    -> 空（树完全相同，测试结果可继承）
```

也就是说走方案 A，公开仓库里既没有令牌、也没有任何含令牌的历史。

### 方案 B（**未采用**，留档）：保留全部历史，先轮换令牌

```powershell
# 轮换本机令牌（会重启网关，手机需要重新扫码/填新令牌）
flix models token --reset
```

对端也轮换一次，然后照常 `git merge --no-ff` + `push`。
- 历史里的旧令牌随轮换失效，泄漏影响归零；
- 代价：两台机器 + 手机都要重新配置令牌。

> 另外可选：`git merge --no-ff` 之后单独 `git push origin main`，
> **不推送 feature 分支**——这样分支提交不进公开仓库。
> 但 merge 提交的父提交仍会在 main 的历史里，令牌依旧可见。所以 A 或 B 才彻底。

### 5.3 极端情况：已经推送后发现必须撤回

```powershell
# 1) 先把 tag 和 Release 撤掉（否则更新器会取到坏版本）
gh release delete v2.6.6 -R XinwangTao/flix-cli -y
git push origin :refs/tags/v2.6.6

# 2) main 上那个 squash 提交：用 revert 而不是 reset
```

> 历史分叉。用 revert 留痕，比抹掉更好。

## 三点九、换包时必须先停看门狗（实测撞车）

本机 `RelayDeskWatchdog` 每 5 分钟跑一次。部署流程是「杀进程 → 拷 exe → 启动」，
如果看门狗正好落在这几步之间，它会自己拉起一个实例，与随后手动启动的那个抢端口
——表现是「刚换完包网关又重启了」，很容易误判成新包有问题。

正确流程（实测有效）：

```powershell
# 1) 先停看门狗
Disable-ScheduledTask -TaskName RelayDeskWatchdog

# 2) 杀进程、拷 exe、启动 serve
Get-Process RelayDesk | Stop-Process -Force
Copy-Item dist_new\RelayDesk.exe dist\RelayDesk.exe -Force
Start-Process dist\RelayDesk.exe -ArgumentList serve,--device-port,18991,--api-port,18998

# 3) 等网关真的健康，再放开看门狗
#    （直接 Enable 也可能被它当成「进程在但网关不响应」而触发第 1 次 strike）
Enable-ScheduledTask -TaskName RelayDeskWatchdog
```

它对「进程在但网关无响应」是 2 次才动手，所以单次慢启动不会被杀——
这也是为什么第 3 步要等健康再放开。

## 三点十五、⚠ 手机 APK 签名不同：官方包装不到本机调试包上

发布前核对签名时发现一件会在发布后才暴露的事：

```
官方 v2.6.5 APK（CI 构建）签名 SHA-256 = 3c34d5a6…e00b2
本机构建 / 手机上已装      签名 SHA-256 = d51c453b…9e688
两者包名相同（com.relaydesk.app.debug），签名不同
```

原因：CI 用 `secrets.ANDROID_DEBUG_KEYSTORE_B64` 还原一个固定密钥库（该 secret
2026-11-17 就有了），而本机 gradle 用的是这台机器自动生成的
`%USERPROFILE%\.android\debug.keystore`（2025-03-24）。两个身份并存。

**后果**：v2.6.6 Release 里那个 APK 直接 `adb install -r` 到这台手机，会报
`INSTALL_FAILED_UPDATE_INCOMPATIBLE`。

### 三条路，按需选

1. **只想继续测试**：不用管。手机上已经是本地构建的 2.6.6（versionCode 20606），
   功能完全一样，`rdProbe` 都在。
2. **要换成官方包**：先卸载再装，配对与模型设置要重做一次：
   ```powershell
   adb uninstall com.relaydesk.app.debug
   adb install RelayDesk-v2.6.6-android.apk
   ```
3. **想以后本地构建与官方一致**（一次性）：把 CI 用的那个密钥库放到本机
   `%USERPROFILE%\.android\debug.keystore`（覆盖前先备份）。之后本地构建出来的
   APK 就能和官方包互相覆盖安装。密钥库内容在 GitHub secret 里，需要你手动导出。

> 校验命令：`apksigner verify --print-certs <apk>` 看 SHA-256 digest。
> 本机 apksigner 在 `%LOCALAPPDATA%\Android\Sdk\build-tools\36.1.0\`。

## 三点十五点五、产物名带 v 前缀（容易看错）

`VERSION` 取自 `github.ref_name`，也就是 tag 名本身 —— **`v2.6.6`，含 v**。
所以 Release 上的资产是：

```
RelayDesk-v2.6.6-win64.zip          RelayDesk-v2.6.6-win64-full.zip
RelayDesk-v2.6.6-macos-arm64.zip    RelayDesk-v2.6.6-macos-x86_64.zip
RelayDesk-v2.6.6-linux-x86_64.zip   RelayDesk-v2.6.6-android.apk
（每个都带 .sha256 侧车）
```

我此前手工演练时按 `RelayDesk-2.6.6-win64.zip`（不带 v）打包，虽然更新器的正则
对**有 v 和没 v 都能匹配**（实测两种都 match=True），但演练产物名与 CI 真实产物
不一致，容易在核对时误判。现统一按带 v 写。

> `release` job 会逐个 `test -f` 校验这 6 个文件与各自的 `.sha256`，缺一个就整单失败。
