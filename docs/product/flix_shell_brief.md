# flix shell 简报（L2 · 局域网远程执行）

## 事实

- 需求：两台已配对设备之间，A 让 B 执行命令并取回结果，等价于局域网 SSH 的最小可用面。
- 现有可复用：8891 设备通道、`pair_devices` 信任表、`/intent` 信封、`flixd` 常驻服务、CLI 与 MCP 两套入口。
- 现状边界：ADB 的 `shell` 明确不通过 MCP 暴露；本项目此前没有任何远程执行能力。

## 范围

**In**：exec 单命令、CLI + MCP 入口、配对即授权、目标端审计、超时与输出上限。
**Out**：交互式 PTY、网页/GUI 终端、公网中继、SSH 密钥兼容层、未配对执行。

## 成功标准（可验收）

1. A 执行 `flix shell <B> -- echo hi`，得到 `hi` 与退出码 0。
2. 未配对设备发起 → 403，B 不执行、不落库。
3. 命令超时 → 进程树被杀，返回 partial + 超时标记。
4. 输出超过 256KB → 截断并置 `truncated`。
5. B 的审计记录能查到：发起方、命令摘要、退出码、耗时。

## 主路径

`flix shell` → 本地配对校验 → `/intent rdShell` → 目标端配对校验 → 执行 → 结果信封 → 渲染退出码 → 审计。

## 关键失败与人工出口

- 未配对（任一端）→ 403，人工查配对状态。
- 超时/超限 → 杀进程树，人工看审计与两端日志。

## 约束

- 目标：Windows 优先（后续 POSIX 同构）。
- 不改现有气泡线格式，新增独立 intent action。
- 不引入密钥体系；信任完全由配对关系承载。

## 借鉴（GitHub 实查，2026-10-31）

- `tailscale/tailscale`：用设备身份授权而非密钥 → 我们把授权落在 `pair_devices`。
- `warpgate`：审计与批准分离 → 执行结果与审计各走一条路径。
- `microsoft/node-pty`：Windows 终端必须走 ConPTY → 二期 PTY 直接用 ConPTY，不自研终端语义。

## 待确认

1. 执行身份：以 `flixd` 当前登录用户运行（默认建议），还是单独低权限账号。
2. MCP 是否允许 AI 自发起执行，还是必须人工先在 CLI 触发。
3. 审计粒度：只记命令摘要 + 退出码，还是连 stdout 一并落库。
