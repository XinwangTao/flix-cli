# 对端机器「整机反复卡死」现场手册

> 适用对象：一台 Windows 11 机器（主机名 `DESKTOP-K087HI9`，局域网 `192.168.237.200`），
> 2026-11-25 当天发生 4 次整机无响应（13:41 / 14:20 / 15:19、16:00 前各有一次，
> 16:02:30 有一条 `Kernel-Power 41` = 未正常关机就重启）。
>
> **结论：这不是 RelayDesk 的问题。** RelayDesk 在该机 CPU 占比约 17%，
> 网关 `/health` 正常、看门狗在 17:01 还成功把掉线的 serve 拉回来过一次。
> 卡死是整机资源层面的，需要在本机处理。

## 一、卡死的典型特征（判断是不是同一类问题）

| 现象 | 含义 |
|---|---|
| `Test-NetConnection -Port 18991` 返回 True，但 HTTP 请求 60s 超时 | 内核还在 ACK，用户态已不服务 |
| `tasklist`、`ping` 这类毫秒级命令也超时 | 整机冻结，不是单个进程忙 |
| 事件日志只有 DCOM 10016 噪音、没有磁盘错误 | 不是磁盘坏道，更像负载/驱动死锁 |
| `Kernel-Power 41` | 上次是硬复位（强制断电/死机） |

## 一点五、先确认它的设备端口（否则会以为「连不上」）

窗口启动服务时是 \8891 if 8891 空闲 else 18991\，所以**端口随机器而变**：

\\powershell
# 只读确认它到底听在哪个端口
Get-NetTCPConnection -LocalPort 8891,18991 -State Listen

# 从你这台机器访问都不写端口也行（默认 8891，连不上会自动试 18991）
flix shell 192.168.237.200 -- cmd /c hostname
\
实测这台对端：serve 跑在 **8891**（+ 18993 网关、18998 API），18991 无人监听。
它的防火墙三个 profile 都开着，但 18991/18993 都有放行规则。

## 二、实测负载画像（2026-11-25 21:4x，只读采样）

| 进程 | CPU | 内存 | 身份 |
|---|---|---|---|
| `CompatTelRunner` | **95%** | 89 MB | Windows 兼容性遥测（父：`InventorySvc`） |
| `python` pid 18004 | **95%** | **1.4→5.8 GB** | `D:\ygx_consumer\consumer.py --loop --interval 10` |
| `ztsmedr` | 29% | 232 MB | Ztsm 终端安全（EDR）实时防护 |
| `powershell` | 21% | 95 MB | `D:\_diag\resource_guard.ps1`（计划任务 `SMT-ResourceGuard`） |
| `powershell` | 11% | 186 MB | `C:\dsh-fix\resource-guard-v3.ps1` |
| `RelayDesk serve` | 13% | 86 MB | 我们自己，**不是问题源** |
| `WXWork` ×4 | — | 2.7 GB 合计 | 企业微信 |

系统总计内存 65 GB、空闲 42 GB、进程数 384。

### 最可疑的一条：`D:\ygx_consumer\consumer.py`

`consumer.py --loop --interval 10`（91 KB 的业务脚本，2026-10-31 修改）的内存会
**冲到 5.8 GB 再回落 1.4 GB**，反复循环。守护脚本的心跳日志记下过：

```
21:39:07 [BEAT] mem=39.6% top=python(18004)=4495MB
21:40:11 [BEAT] mem=42.5% top=python(18004)=5807MB
21:41:15 [BEAT] mem=35.3% top=python(18004)=1367MB    <- 被回收/被杀
```

6 GB 的内存尖峰本身压不垮 65 GB 的机器，但它每次尖峰都会让 **EDR 实时防护去扫描
这个堆**——两者叠在一起就是整机级别的停顿。这是目前最像「冻结」成因的组合。

### 第二个可疑点：三个功能重叠的守护脚本

| 任务 | 脚本 | 状态 |
|---|---|---|
| `SMT-ResourceGuard` | `D:\_diag\resource_guard.ps1` | **Running**（常驻） |
| `PCCrashGuard` | `C:\Users\Administrator\AppData\Local\PCCrashGuard\guard.ps1` | **Running** |
| （无任务名） | `C:\dsh-fix\resource-guard-v3.ps1` | 运行中 |

后两个的注释写明它们会「按规则杀掉危险进程，内存吃紧时杀掉最大的非白名单进程」。
**杀进程本身就会制造不稳定**；三个脚本互相不知道对方在做什么，很容易误杀。
（`RelayDeskServeWatchdog` 现在是 Disabled 状态，说明有人动过。）

### 第三个：企业安全软件 `Ztsm`

`C:\Program Files (x86)\ZtsmEnt\108.7.32942.62003`，三个服务常驻：
`ztsmemgsvc`、`ztsmrtp`（实时防护）、`ztsmwscsvc`。带 `LoadHotPatchx64.exe`
（内核热补丁）。这类内核过滤驱动 + 大内存进程扫描是已知的冻结来源。

## 三、建议的处理顺序（按 21:4x 实测证据排优先级）

> 全部是**只读确认 + 你自己决定是否执行**。我不在这台机器上改任何东西。

### 1. 先治 `D:\ygx_consumer\consumer.py` 的内存尖峰（第一优先）

它是当前唯一有「内存涨到 5.8 GB」证据的进程，也是唯一会被守护脚本杀掉的进程。

```powershell
# 只读：确认它现在的内存与谁在拉起它
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
    Where-Object { $_.CommandLine -match 'ygx_consumer' } |
    Select-Object ProcessId, ParentProcessId, CommandLine
```

可选做法（按代价从低到高）：
- 把 `--interval 10` 放宽（比如 60），降低尖峰频率；
- 在 `consumer.py` 的循环里加 `gc.collect()`，或查它是否把整批数据一次性读进内存；
- 暂时用 `Stop-ScheduledTask` 停掉它的计划任务，观察一天机器是否还冻结
  —— **这是最快的「是它还是别的东西」判定**。

### 2. 关掉 Windows 兼容性遥测（第二优先，零风险）

`CompatTelRunner` 长时间 95% CPU，主要开销在磁盘扫描：

```powershell
# 只读确认
Get-ScheduledTask -TaskPath '\Microsoft\Windows\Application Experience\*' |
    Select-Object TaskName, State

# 关掉（需要管理员）
Disable-ScheduledTask -TaskName 'Microsoft Compatibility Appraiser' -TaskPath '\Microsoft\Windows\Application Experience\'
Disable-ScheduledTask -TaskName 'ProgramDataUpdater' -TaskPath '\Microsoft\Windows\Application Experience\'
```

### 3. 只留一个守护脚本，删掉其余两个

三个脚本各占 11–21% CPU，而且**会杀进程**——它们本身就是不稳定源。

```powershell
# 看清楚有哪些
Get-ScheduledTask | Where-Object { $_.Actions.Arguments -match 'guard' } |
    Select-Object TaskName, State, @{n='Args';e={($_.Actions.Arguments) -join ' '}}
```

保留一个（推荐留 `PCCrashGuard`，它的注释最完整、有白名单），另外两个：
`Disable-ScheduledTask -TaskName 'SMT-ResourceGuard'`，并把
`C:\dsh-fix\resource-guard-v3.ps1` 对应的任务一起停掉。

### 4. 和 IT 确认 `Ztsm` 终端安全能不能加排除项

`ztsmrtp` 是实时防护。它每次扫描那个 6 GB 的 python 堆，就是整机停顿的放大器。
如果这是公司的强制安全软件，**不要自己卸**——找 IT 给
`D:\ygx_consumer\`、`D:\auto\`、`RelayDesk.exe` 加扫描排除。

### 5. 其余（按需）

- 自托管 runner：`Get-Service 'actions.runner*'`，确认不跑 CI 时 `Stop-Service`。
- 堆积会话：`Get-Process claude, python, pythonw, node` 看启动时间，关掉没人看的。
- 深信服：`SangforVnic` 在跑但没有 EasyConnect 客户端，若上面都做了仍冻结，
  再考虑完整卸载观察一天。

## 三点五、给对端换包时的三个坑（2026-11-25 23:4x 实测）

### 1. `flix send` 不会覆盖同名文件

它会在对端生成 `name (1).ext`、`name (2).ext`。于是「发新版脚本过去」很可能
**还是旧文件在跑**，日志里看到的报错来自上一版。要么每次用唯一文件名
（如 `rd_upd_a2.ps1`），要么先删掉旧的。

### 2. 远端 `.ps1` 必须纯 ASCII

PowerShell 5.1 会把**没有 BOM 的 .ps1 当 ANSI 读**，脚本里的中文变成乱码，
整份解析失败：

```
所在位置 ...peer_apply_update.ps1:71 字符: 110
表达式或语句中包含意外的标记 "鏈未缃?"
```

加 BOM 也能解决，但很容易在某次编辑/传输里丢掉。**把远端脚本写成纯 ASCII
（日志也用英文）是唯一稳的做法**——这个文件已经因为中文栽过两次。

### 3. 换完包设备端口会变

对端原来跑在 8891（窗口启动时 8891 空闲），换包脚本用
`serve --device-port 18991` 启动，所以换完 **8891 不再监听、18991 开始监听**。
好消息：`flix shell <ip>` 不写端口也会自动试另一个候选端口（本轮实测直接连上）。
它防火墙对 18991/18993 都有放行规则，18998 可能没有（所以 API 端口连不上是正常的）。

## 三点七、schtasks 一次性任务会「跑两次」（00:1x 实测）

用 `schtasks /Create /SC ONCE /ST 23:59` 建任务再 `/Run`，结果是：

```
23:42:20  backup -> RelayDesk.exe.prev-20261125-234220   <- 手动 /Run
23:59:14  backup -> RelayDesk.exe.prev-20261125-235913   <- 计划时间自己又跑了一次
```

换包干了两次。对端网关在 23:59 又重启了一回，看起来像「刚升级完就自己重启」，
很容易误判成新包有问题。**实际是我建任务时把 `/ST` 设成了十几分钟后的时间。**

正确做法（任选）：

```powershell
# A) 计划时间放到很久以后，只靠手动 /Run
schtasks /Create /TN X /TR "..." /SC ONCE /ST 23:59 /SD 2099-01-01 /F
schtasks /Run /TN X
# 确认跑完再删掉，避免以后误触发
schtasks /Delete /TN X /F

# B) 或者跑完立刻删
```

判断有没有重跑：看更新日志里出现过几次 `=== start ===` / `replaced`。

## 四、RelayDesk 侧的兜底（已做好，不用你管）

- **开机自启**：登录即起 `serve`（Startup 里的 `RelayDeskServe.vbs`）。
- **看门狗**：计划任务 `RelayDeskWatchdog` 每 5 分钟检查，serve 掉了自动拉起
  （17:01 实际生效过一次）；连续 2 次「进程在但网关不响应」会强杀重启。
- **级联中继**：该机不登录 VPN 也能用模型 —— 网关上游指向有 VPN 的那台
  （`http://192.168.237.7:18993`），实测 39→11 个可用模型、补全正常。
- 日志：`%TEMP%\relaydesk-watchdog.log`（健康时不写，只有动作才记）。

> 注意：**整机冻结时看门狗也救不了**（Task Scheduler 同样被冻住）。
> 只有「RelayDesk 进程死了但系统还活着」这种情况能自愈。

## 五、验收标准

处理完后连续观察 2 小时：

```powershell
# 本机（有 VPN 的那台）
flix models doctor --watch 7200 --interval 120
```

期望：`模型数` 恒定、`新增失败 0`、`active` 不增长。
对端用 `192.168.237.200:18993/v1/models` 访问应保持 200（模型数与该机一致）。
